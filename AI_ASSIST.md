# AI Assistance

The brief asks *"how you used AI, and your judgment in applying the output."* This is the honest answer, kept short on purpose.

## Tools

| Tool | Role |
|---|---|
| **Claude Sonnet 4.6** (via Claude Code CLI) | Planning, spec writing, code generation, iterative refactors |
| **Claude Code sub-agents** | Parallel pre-planning research on Open-Meteo, backend stack, frontend stack, testing, architecture, UI/UX |
| **GitHub Copilot** (in-editor) | Line-level completions during coding sessions |

## Methodology: spec-driven, plan-then-execute

The workflow was not "chat with the model and paste whatever it says". Every non-trivial piece of code went through the same loop:

1. **Spec first.** [`specs/`](specs/) has 9 formal specs (00–08) — architecture, domain, scoring, adapters, GraphQL, testing, UI/UX, use case. Each was written and reviewed *before* the code it describes existed. Each spec has a *Rejected alternatives* table so a reviewer can see the design space, not just the destination.
2. **AI drafts a plan.** Given the spec + current repo state, the model proposed an implementation plan (file list, order of operations, gotchas). I reviewed and adjusted before code generation.
3. **Execute + review file-by-file.** No blind acceptance of multi-file diffs. Every generated file was read line-by-line.
4. **Tests as the acceptance criterion.** Property-based tests on the scorers (`fast-check`), integration tests through the real use case with mocked HTTP (`undici.MockAgent`), Playwright E2E, `@axe-core/playwright` for a11y. If the output couldn't survive those, it didn't ship.

Artefacts of the workflow that ship with the repo:
- [`specs/`](specs/) — 9 specs, written before code.
- [`research/`](research/) — 6 pre-planning research reports, each generated by a sub-agent from a targeted prompt (e.g. [01-open-meteo-api.md](research/01-open-meteo-api.md), [05-architecture.md](research/05-architecture.md)).

## Where AI drove

Non-controversial decisions where the model's recommendation matched the industry default and my own instinct:

- **Hexagonal / ports & adapters** layout for the backend.
- **Pothos** for code-first GraphQL — better TS inference than TypeGraphQL, no decorators, still emits SDL.
- **`fast-check`** for property-based tests on scoring — bell-curve maths is a textbook property-test target.
- **`undici.MockAgent`** for HTTP mocks (built into Node 22, intercepts native `fetch()`).
- **`useSuspenseQuery`** + fragment masking on the frontend (Apollo Client 3's Suspense direction, which pairs naturally with React 19).
- **OKLCH tokens** for the activity-reactive palette — perceptually uniform interpolation, no muddy midtones.

The signal here: I asked, I checked the reasoning against what I'd have picked myself, and moved on.

## Where I overrode

The load-bearing part of this document. Categories where AI's default was wrong for this context:

- **Stack theatre.** AI reflexively suggested Yoga, `axios`, `p-retry`, `nock`, Redux, InversifyJS, and Turborepo at various points. Each is defensible in the right project. None was right *here* — three packages, one team, one deploy target, no independent release cadence. Chose Apollo Server, native `fetch`, an inline retry loop, `undici.MockAgent`, Apollo cache + React Context, a hand-written composition root, and `pnpm -r`. Every rejection is documented in the relevant spec's *Rejected alternatives* table with the trigger point (e.g. Turbo pays off with 10+ packages and cross-machine cache; we have 3 packages and 1 CI runner).
- **Scope creep dressed as features.** A 3D globe empty state. A full Pact Broker with `can-i-deploy` gates. A multi-browser Playwright matrix. Each would have inflated the demo without moving the reviewer's criteria. Kept a minimal, honest version of each (suggested-city chips; single consumer → provider Pact roundtrip; Chromium-only E2E) and flagged the "here's when the full version matters" as trade-offs in the README.
- **Numeric hand-waving.** AI generated scoring weights like `snowfall: 0.5` without citing anything. I re-derived from domain sources (Surfline, OnTheSnow, Snow-Forecast, WHO AQI guidelines) and left comments in the scorer code so a reviewer can audit each number. Weights are grounded, not vibes.
- **Security shortcuts.** AI suggested baking an Anthropic key into the repo "so it works out of the box". Non-starter. Instead: opt-in `ANTHROPIC_API_KEY` env var, deterministic template fallback when unset, `$2/mo` hard cap in the Anthropic console, kill switch at 100 successful summaries/day, per-city 30-min cache, 3s timeout with no retries.

## Where AI clearly saved time

- **Open-Meteo API mapping** — the sub-agent's endpoint/variable dump saved hours of docs reading. I verified critical facts (rate limits, marine coverage inland) against live API responses before writing adapters.
- **Zod schemas from response fixtures** — feed one saved JSON, get a matching schema back. Avoids manual typing tedium and is easy to review.
- **Playwright role-based selectors** — the model wrote `getByRole('combobox', { name: /city/i })` correctly on first pass; I'd have looked up the syntax.
- **Editorial prose** — turning bullet lists into flowing text in specs and README while keeping tone consistent.

## Guardrails that kept AI honest

- **Specs before code, not after.** If AI's suggestion violated the spec, the spec won — or the spec was amended in a review pass with the *why* logged before code changed.
- **Line-by-line file review.** Caught, in review, things that never reached the repo: `apollo-server` v3 (EOL) instead of `@apollo/server` v5; retrying 4xx errors with `p-retry`; an unnormalised geocoding cache key; a stray `useEffect(() => fetch())` when Apollo was already wired.
- **Tests as the arbiter.** When AI insisted the code was correct and tests disagreed, tests won. Example: the Marine adapter's `cell_selection=nearest` default returns `null` wave heights inside bays where the nearest grid cell is on land. The Zod schema failed loudly instead of silently mapping to zero, and the fix (`cell_selection=sea`) came from that signal.
- **Rejections and trade-offs live in the docs.** Every "we didn't do X because Y" is in a spec, this document, or the README's trade-offs section — not in my head or a Slack DM.
